# 🌌 12306 现代票务分配与客流调度综合解决方案 (Comprehensive Ticketing & Flow Dispatch Solution)

本设计方案旨在解决 12306 这一千古难题下“多站区间复用引发的漏斗吞噬效应”、“热门区间阻断长途客流”、“中转不便导致客流流失”等核心商业复杂性问题。

方案通过将**多级水库配额管理、时空展开图搜索、运筹学候补拼装、分布式 Saga 原子锁座以及最终投影一致性**进行高内聚合龙，构建出兼顾系统商业收益（Revenue）与社会公平运力（Fairness）的立体化调度中枢。

---

## 1. 席位库存的“动态水库”配额管理模型 (Dynamic Reservoir Quota Management)

### ❓ 1.1 区间冲突与漏斗吞噬效应 (The Funnel Devouring Effect)

在多站列车客运网络中（如：北京 ──► 天津 ──► 济南 ──► 上海），短途、高频的爆满客流（如北京-天津）在发售瞬间会迅速吞噬整车的物理席位，从而切断了长途高客单价（如北京-上海）的通铺线路。这不仅严重流失了客运收益，而且在列车开行过中途站（天津）后，会导致后半程出现大面积的空座（“断腿空驶”）。

```text
  北京 (Seq 1) ──────────► 天津 (Seq 2) ──────────► 济南 (Seq 3) ──────────► 上海 (Seq 4)
  ┌──────────────────────────────────────────────────────────────────────────────┐
  │                            全程长途客流 (北京 ──► 上海)                      │  ──► [ 高票价 / 高运力利用 ]
  ├──────────────────────────────┼───────────────────────────────────────────────┤
  │      短途 A (北京 ──► 天津)  │                 短途 B (天津 ──► 上海)        │  ──► [ 低单价 / 易产生断腿空置 ]
  └──────────────────────────────┴───────────────────────────────────────────────┘
```

### 💡 1.2 多级蓄水池划分与时间窗滑动释放 (Dynamic Quota Sliding)

本方案不采取机械的“物理席位锁死限制”，而是将单列车次的座位状态库抽象为流动的逻辑水库配额隔离池：

```text
  【发售初期】(离起跑 > 7 天)
  ┌───────────────────────────────────────────────┐
  │ 专售池 (Exclusive Pool) - 80% 专供长途通铺旅客 │  ──► 拦截并降级短途购票请求至【候补/中转】
  ├──────────────────────────────┬────────────────┘
  │ 共享池 (Shared Pool) - 10%    │ 限售池 (Short-Haul Throttled) - 10% (京津微量票)
  └──────────────────────────────┴────────────────────────────────┘
  
  【发车前 3 天】(长途需求基本释放完毕)
  ┌───────────────────────────────────┬───────────────────────────┐
  │ 专售池 (Long-Distance Only) - 30%  │ 共享池 (Shared Pool) - 70% ──► 动态并入，满足高频中短途
  └───────────────────────────────────┴───────────────────────────┘
  
  【发车前 24 小时】(最后清仓期)
  ┌───────────────────────────────────────────────────────────────┐
  │ 共享公共池 (Shared Pool) - 100%                               │  ──► 彻底扁平化，有空即售
  └───────────────────────────────────────────────────────────────┘
```

*   **配额滑动调度公式**：
    
    `[ 动态释放比例 ] = 1.0 - ( 1.0 - 基础释放率 ) * ( 1.0 - e ^ ( - 衰减指数 * 离发车小时数 ) )`
    
    系统实时感知离发车小时数。当离发车时间临界触发时，长途物理隔离席位（即 `is_long_distance_pool = True`）按时效批量被批量刷写为 `is_long_distance_pool = False`，无缝导入共享池。

## 2. 运筹学背包候补拼装引擎 (Operations Research Knapsack Waitlist Engine)

当短途旅客购票请求因前期配额限制而遭受拦截时，系统引导其进入带有预授权扣款的**候补队列（Waitlist Queue）**。

### 🧩 2.1 碎片化余票拼装 (Bin Packing Connection)

后台高并发调度中心运行一个专门的异步背包拼装引擎。它通过多队列时间对齐扫描，探测是否能通过“短途拼装”填满长途空闲。

```text
  候补队列碎片：
  - 候补 A：[北京 ──► 天津] (Seq 1->2)
  - 候补 B：[天津 ──► 济南] (Seq 2->3)
  - 候补 C：[济南 ──► 上海] (Seq 3->4)
  
  ┌─────────────────────────────────────────────────────────────┐
  │                  未售出的闲置长途物理座席 (Seat 01A)           │
  └─────────────────────────────────────────────────────────────┘
                                 │
                                 ▼ [ 拼装引擎 10s 一次原子合拢 ]
  ┌─────────────────────────────┬──────────────┬────────────────┐
  │  分配给 A (Seq 1->2)         │分配给 B (2->3)│ 分配给 C (3->4) │
  └─────────────────────────────┴──────────────┴────────────────┘
```

*   **原子兑现控制**：
    该合拢拼装行为在数据库侧通过单笔隔离事务一次性落库。它读取多名连续短途候补旅客的请求，并在锁定 Seat 01A 全区间段（111）后，同时向三名旅客下发出票，物理运力完美吃满，客票收益最大化。

## 3. “航空级”时空展开联程路由 (Aviation-Grade Time-Expanded Transfer Routing)

当单车次直达运力确实物理耗尽，或者两站之间本无直接直达车次时，系统启动**航空级中转联程推演网络**。

### 🧭 3.1 时空有向展开图 (Time-Expanded Route Graph)

系统引入时空图计算模型。图中的每一个节点包含两个维度：`( 车站, 时刻 )`。

```text
  [ 北京南站 ] (14:00) ──► Train G101 (1.5h) ──► [ 济南西站 ] (15:30)
                                                       │
                                                       │ ──► [ 站内便捷中转通道 ]
                                                       │     ( 满足 MCT 约束: >= 30分钟 )
                                                       ▼
  [ 上海虹桥 ] (18:30) ◄─── Train G555 (2.5h) ◄─── [ 济南西站 ] (16:00)
```

### ⏱️ 3.2 最小中转时间窗校验 (Minimum Connecting Time)

系统为每个一等枢纽站维护一个 MCT 矩阵（如同机场联程）：
*   **同台中转 (MCT_Same)**：下车后对面站台直接上车，MCT 限制时间为 `>= 10` 分钟。
*   **便捷通道中转 (MCT_Pass)**：走地下或天桥便捷中转专用道，MCT 限制时间为 `>= 20` 分钟。
*   **同城异站中转 (MCT_Cross)**：从北京南站到北京西站，MCT 需计入地铁/地面交通损耗与二次安检时间，限制时间为 `>= 90` 分钟。

### 🛡️ 3.3 动态延误对冲 (Delay Protection Factor)

为防范前段列车延误导致后段衔接断裂、造成旅客滞留，系统引入延误权重：

`MCT_Safety = MCT_Base * ( 1.0 + 历史车次延误率 * 恶劣天气系数 )`

当华东地区遭遇大风或雷雨，Train 1 的历史晚点概率激增时，路由系统自动拓宽济南西站的中转判定窗口，优先向旅客推荐 45 分钟以上的宽余换乘组合，防止行程中断。

## 4. 全局分布式事务席位锁定与聚合支付 (Distributed Saga Orchestration)

中转联程、同车断配换座涉及**两段或多段物理独立席位**的扣减与支付。

### ⛓️ 4.1 原子锁座设计 (Saga Orchestration)

绝不允许出现“买到第一段、第二段却被抢占”的半残废现象。购票必须在锁座阶段实现 Saga 全回滚协调：

```text
                          [ Saga Orchestrator ]
                       (发起多段中转/拼装一键原子预占)
                                  │
                  ┌───────────────┴───────────────┐
                  ▼ (Phase 1: Lock)               ▼ (Phase 1: Lock)
          [ T1 席位读写锁模型 ]           [ T2 席位读写锁模型 ]
          (段 1: Seq 1->2 掩码)           (段 2: Seq 2->4 掩码)
                  │                               │
                  └───────────────┬───────────────┘
                                  ▼
                      ( 联合判定: 是否两段均成功? )
                                  │
            ┌─────────────────────┴─────────────────────┐
            ▼ (YES: 两段全中)                            ▼ (NO: 任意段冲突/售罄)
    [ 确认整体预占并生成订单 ]                   [ 触发 Saga 逆向补偿回滚 ]
    - 写入本地 Outbox 归档                       - 若 T1 成功：释放 T1 (段 1 掩码回零)
    - 统一支付单结算：                           - 若 T2 成功：释放 T2 (段 2 掩码回零)
      ¥ [Price T1] + ¥ [Price T2]                - 向前端返回锁座失败，不扣一分钱
```

### 💸 4.2 聚合支付与清算中心 (Unified Billing)
*   **一单付款**：对旅客合并展示总结算价格，单笔订单调起银行扣款。
*   **局端清算（Settle）**：在系统后台，通过统一结算账户，自动根据行驶里程、担当路局（如北京局、上海局）完成财务分成切分。

## 5. 旅客购票拦截与分流“智能漏斗” (Traffic Funnel Flowchart)

本系统在最外围建立高吞吐漏斗，将大流量平滑引流至替代运力，极致发掘物理铁路资产的使用上限：

```text
       [ 旅客 A 发起购票请求: Beijing ──► Shanghai ]
                        │
                        ▼
            /────────────────────────\
           <   1. 直达列车是否有直达票?   > ───────YES──────► [ 极速直达出票 ]
            \────────────────────────/
                        │ NO
                        ▼
            /────────────────────────\
           <   2. 该车次能否同车分段换座? > ───────YES──────► [ 同车中转换座出票 (EPIC-06) ]
            \────────────────────────/                         ( 01A -> 廊坊 -> 05C 接力 )
                        │ NO
                        ▼
            /────────────────────────\
           <   3. 枢纽网络是否有中转联程? > ───────YES──────► [ 航空级一键联程出票 ]
            \────────────────────────/                         ( 购买 G101 + G555 联程票 )
                        │ NO
                        ▼
            /────────────────────────\
           <    4. 旅客是否接受进入候补?  > ───────YES──────► [ 进入候补队列，等待 OR 背包拼装 ]
            \────────────────────────/
                        │ NO
                        ▼
                [ 返回完全售罄 / 推荐明日行程 ]
```

## 6. SRE 与可观测性核销指南 (DevOps Deployment Guide)

1.  **冷热隔离部署**：
    *   **交易服务（写模型）**：分配至独立写节点群，直连带有高物理行锁约束的 MySQL 与高性能 Redis Sentinel。
    *   **时空展开路由（中转推荐）**：由于采用 A* 启发式图搜索或时序 Dijkstra 算法，计算较为吃 CPU，需独立部署在计算节点集群，避免其网络推演抢占写事务数据库连接。
2.  **发件箱（Outbox）高并发消费**：
    *   所有因配额调整、拼装或中转换座产生的底层物理事件均产生 `outbox`。
    *   以 `SKIP LOCKED` 高频率并发轮询发件箱，零阻塞投递至 Kafka，确保读写投影（Redis Bitmap 缓存）一致性时间延时 `< 50` 毫秒。

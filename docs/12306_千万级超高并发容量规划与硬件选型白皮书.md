## 2. 5千万级 (50M) 极限流量目标拆解 (The 50M CQS Deconstruction)

**5千万次/秒 (50,000,000 QPS/TPS)** 是超越双十一峰值数倍的极致海量并发。在真实的 12306 场景中，绝大多数流量来自于用户的疯狂刷新（读）。根据二八定律与实际购票漏斗，我们按照 **99% 读流量与 1% 写流量** 进行物理拆解：

*   **总峰值吞吐**：50,000,000 CQS (Command Query per Second)
*   **读峰值 (Query)**：`49,500,000 QPS` (4950 万次查询/秒)
*   **写峰值 (Command)**：`500,000 TPS` (50 万次下单预占/秒)

要支撑这一量级，单中心静态配置必定崩溃，必须引入 **异地多活 (Active-Active Multi-Region)** 与 **边缘计算极光防御** 体系。

## 3. 数据库与分布式缓存存储容量估算 (Storage Sizing)

### A. 每日 MySQL 基础配席数据（静态与段锁数据）
每日开行 1000 趟车，每趟 1000 个座席，产生 1,000,000 个物理 Seat 记录。由于列车包含 15 个站，产生 14 个物理区间段（Segment Locks）。

#### ① 单条 SeatSegment 记录存储开销：
```text
  字段名称 (Field)       类型 (Type)          物理大小 (Bytes)
  id                     INT (Primary Key)    4
  schedule_id            INT (Foreign Key)    4
  seat_id                INT (Foreign Key)    4
  segment_no             TINYINT              1
  state                  VARCHAR(10)          10
  version                INT                  4
  -----------------------------------------------------------
  物理小计 (Row Size)                         ~27 字节 (考虑 InnoDB 页头与指针折合为 64 字节/行)
```

#### ② 每日段锁表记录数及存储体积：
```text
  [ 每日记录数 ] = 1,000 趟 * 1,000 席 * 14 段 = 14,000,000 行/天 (一千四百万行)
  [ 每日数据量 ] = 14,000,000 行 * 64 字节 = 896,000,000 字节 ≈ 896 MB/天
  [ 每日索引与元数据开销 (100% 冗余) ] ───────► 896 MB * 2 = 1.79 GB/天
  [ 年度物理存储总量 (Yearly Metadata) ] ─────► 1.79 GB * 365 ≈ 653 GB/年
```

---

### B. 每日购票事务数据（订单、票扣、发件箱）
每日成功售出 50,000,000 张车票（即 Command 事务）。产生 5000 万个 Ticket 记录、约 2500 万个 Order 订单记录（假设一次订单平均买 2 张票）以及 5000 万个 Outbox 发件箱事件记录。

#### ① 单条记录物理大小估算：
*   `Ticket` 行大小：约 **128 字节**（含车票号、车次、座位 ID、乘车人 ID、票价、状态）。
*   `Order` 行大小：约 **256 字节**（含订单号、支付流水号、总价、状态、创建时间）。
*   `Outbox_event` 行大小：约 **512 字节**（含事件全局唯一 ID、类型、聚合 ID、状态、JSON payload 契约体）。

#### ② 每日交易数据存储增量：
```text
  [ Ticket 每日大小 ] = 50,000,000 * 128 字节 = 6.4 GB/天
  [ Order 每日大小 ]  = 25,000,000 * 256 字节 = 6.4 GB/天
  [ Outbox 每日大小 ] = 50,000,000 * 512 字节 = 25.6 GB/天
  -------------------------------------------------------------
  [ 纯数据每日小计 ]                         = 38.4 GB/天
  [ 索引、冗余与事务日志 (MySQL Binlog/Undo, 150% 冗余) ] ─► 38.4 * 2.5 ≈ 96 GB/天
  [ 年度事务数据总量 (Yearly Transactions) ] ──► 96 GB * 365 ≈ 35,040 GB ≈ 35.04 TB/年
```

> **MySQL 存储选型建议**：
> 每日 96 GB 写入，一年沉淀 **35 TB** 强事务数据。
> 1. 采用 **MySQL 256个物理分片集群（Sharding）**，单物理分片承载 `35 TB / 256 ≈ 140 GB/年` 的轻量级存储，完美发挥 PCIe-4.0 NVMe SSD 的极致 IOPS 优势。
> 2. 对历史完结订单、已被 Projector 投影并消费成功的已处理发件箱事件（`processed=1`），由后台归档 Cron 线程每周定时迁移至冷数据层（如 Apache Iceberg / Hive 历史温区），主库只保全近 30 天的最热在线高并发活跃数据，主库磁盘水位长效锁定在 **5 TB** 以内。

### C. 分布式缓存内存估算 (Redis Memory Sizing)
高并发读写分离（CQRS）下，全量最热列车的区间二进制占用位掩码（Bitmask）与快速可用余票统计，100% 缓存在 Redis Cluster 中。
*   保持最近 15 天开行的所有车次完全在 Redis 内存中。
*   活跃车次总数 = 1000 趟/天 * 15 天 = 15,000 趟列车。

#### ① 席位区间位掩码哈希（r:{sched_id}:seat:{id}）
15,000 趟车 * 1000 个物理席位 = 15,000,000 个活跃席位 Key。
每个 Key 值为二进制整数（15个站，14个位，仅需 2 字节存储）。由于 Redis 内存分配器的内存对齐 Overhead，折合消耗约 **150 字节/Key**：
```text
  [ 席位位掩码内存总量 ] = 15,000,000 * 150 字节 = 2,250,000,000 字节 ≈ 2.25 GB (极轻量)
```

#### ② 快速查询余票 Hash（q:availability:{sched_id}）
15,000 趟车 * 6 种座位席别 = 90,000 个余票缓存 Key。每个 Hash 约消耗 **12 KB**：
```text
  [ 快速余票 Hash 内存总量 ] = 90,000 * 12 KB ≈ 1,080,000 KB ≈ 1.08 GB
```

> **Redis 内存选型结论**：
> 全系统最核心的抢票和余票读缓存在 Redis 内仅消耗 `2.25 + 1.08 ≈ 3.33 GB` 内存。
> 12306 的 Redis 集群瓶颈根本不是内存容量（Capacity），而是单线程在万级高并发下执行 Lua 脚本的吞吐极限（IOPS）。硬件选型时应优先选择高主频、低内核数的 CPU（如单核 4.0GHz+）充当 Redis Master 节点，并利用物理分片均摊 QPS。

## 4. 读写双侧架构演进与扩展规划 (Architectural Evolution)

### A. 读侧架构演进：4950 万 QPS 的三级缓存防御圈 (Query Defense)
不能让 4950 万 QPS 穿透到机房核心 Redis，必须将计算与缓存推向边缘与进程本地。

```text
  [ 49,500,000 QPS 狂暴读流量 ]
             │
             ▼ 1. 边缘节点防御 (CDN / Anycast 智能网关) ──────► 拦截 60% (约 30M QPS)
             │    - 返回前一秒的短时效静态余票快照。
             │
             ▼ 2. 本地内存网关 (L1 Cache: Nginx Dict / 进程内存) ─► 拦截 30% (约 15M QPS)
             │    - 部署 5000+ 无状态网关节点，接收 Kafka Projector 的 Pub/Sub 余票广播，
             │      直接在进程内存中返回 0 毫秒延迟数据。
             │
             ▼ 3. 分布式缓存中心 (L2 Cache: Redis Cluster) ─────► 最终承接 10% (约 4.5M QPS)
                  - 承接最实时的点对点长连查询，物理拆分成 100 个分片 (Shards)。
                  - 单 Shard 承担 45,000 QPS，处于 Redis 极度舒适的安全水位。
```

### B. 写侧架构演进：50 万 TPS 的异步排队与数据分片 (Command Sharding)
50 万 TPS 的物理落盘不可能由单一或少量的 MySQL 集群承担。必须采用 **排队削峰 + Lua分片扣减 + MySQL 细胞化分片**：

#### ① 极速排队机与写流控 (Virtual Waiting Room)
在进入 Redis 扣减前，引入类似 Nginx 层或前置网关的排队机（Token Bucket）。将超出 50 万 TPS 的海量无效恶意点击拦截在门外，对合法请求下发 Token 排队号，削峰填谷。

#### ② Redis 分片预占拦截 (Lua Bitmask Sharding)
*   将当前的 Redis 单点升级为 Redis Cluster 分片集群 (如 256 个 Shard)。
*   **路由规则**：按 `(Train_ID, Date)` 作为哈希槽 (Slot) 的 Routing Key。由于不同车次的数据绝不相交，可完美打散到 256 个节点上。单台 Redis 处理 2,000 TPS 的 Lua 位掩码，256 台完美吞下 500,000 TPS 峰值扣减。

#### ③ MySQL 细胞化分表落盘 (Cellular Database Sharding)
50 万次物理落盘/秒，按单机极值 2,000 TPS 算，需将数据库进行极致水平切分。
*   **分库分表维度**：采用 `Hash(schedule_id) % 256` 拆分出 **256 个物理 Database 集群 (一主多从)**。
*   每个主库仅需承担 `500,000 / 256 ≈ 1,953 TPS`，这一压力对于启用了 NVMe 固态的高性能 MySQL 节点毫无压力，行锁升序（ASC）机制依然 100% 生效，死锁率为 0！

## 5. 网络带宽与消息队列物理容量估算 (Network & Kafka Sizing)

### A. 网络物理带宽估算
*   **读侧 QPS 带宽**：在 49,500,000 QPS 读峰值下，每次 `GET /api/v1/query` 响应的极简 JSON 报文包大小按 200 字节算：
    ```text
      [ 读侧网络物理带宽 ] = 49,500,000 * 200 字节 * 8 = 79.2 Gbps (万兆网络将瞬间爆裂塞满！)
    ```
    *SRE 减压策略*：通过 CDN 和 L1 进程内存拦截 90% 的请求。穿透至中央机房核心的 QPS 骤降至 4,950,000 QPS，核心网络带宽降为 **7.92 Gbps**，机房光纤专线安全无虞。
*   **写侧 TPS 带宽**：在 500,000 TPS 并发预占/打单峰值下，每次 POST 购票请求报文与账单响应总和约 1,000 字节：
    ```text
      [ 写侧网络物理带宽 ] = 500,000 TPS * 1,000 字节 * 8 = 4 Gbps (需要核心机房具备千兆级局域专网)
    ```

### B. 消息队列 (Kafka Partition Sizing)
所有的交易事务（50,000,000 次/天）通过 Outbox 事件投递到 Kafka 主题 `ticket_events` 中。

```text
  [ MySQL Transaction ] ──► (写本地 Outbox 表) ──► [ CDC Binlog 解析器 ]
                                                          │ (Binlog 增量抓取，主库0开销)
                                                          ▼
                                                    [ Kafka Topic ] 
                                                   (ticket_events)
                                                   (32 Partitions)
                                                          │ (按 Schedule_ID 严格保序)
                                                          ▼
                                                    [ Projector ] ──► (批量 HSET Redis)
```

*   **分发保序**：物理硬锁 Kafka 主题 `ticket_events` 拥有 **32 个 Partitions**（对齐 KEDA 最大 32 消费副本）。
*   **消息路由**：一律以 `schedule_id`（车次计划ID）为 Key 进行 Hash 路由，确保**同一车次的所有事件（出票/退票/候补）强制路由进同一个分区内部**，彻底规避了因多分区并行乱序造成的读缓存覆盖脏态。
*   **积压容量（7天保留期）**：
    `50,000,000 * 512 字节 * 7天 ≈ 179.2 GB` 的轻量高速硬盘空间。

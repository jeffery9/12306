# 🌌 12306 高并发区间段位图 (Bitmap) 预占核心设计方案

本文件详细阐述了本项目针对中国铁路 “一车多站、区间席位复用、长途短途运力冲突” 这一核心世界级高并发难题的物理设计与算法底座。整个方案由 **“写侧 Redis 二进制位掩码极速预占（第一防御线）”** 与 **“MySQL 物理区间段级升序行锁（第二防御线）”** 构成。

---

## 1. 业务痛点与技术建模分析

### 1.1 区间座位复用难题
设有一趟复兴号列车 G888 次，经停 4 个站，共有 3 个物理区间：

```text
  站序列：     [北京] (Seq 1)  ──►  [天津] (Seq 2)  ──►  [济南] (Seq 3)  ──►  [上海] (Seq 4)
  物理区间：             [ 区间段 1 ]         [ 区间段 2 ]         [ 区间段 3 ]
```

- **座位复用**：若旅客 A 预订了 [1 ──► 2] (北京-天津)，旅客 B 预订了 [2 ──► 4] (天津-上海)，他们可以被分配到**同一个**物理座椅（例如 01A）。运力周转率提升至 200%。
- **区间冲突**：若旅客 C 预订了 [1 ──► 3] (北京-济南)，由于其购买路径覆盖了 [区间段 1] 和 [区间段 2]，此时 A 无法购买 [1 ──► 2]，B 无法购买 [2 ──► 4]，产生排他性硬件冲突。

### 1.2 传统方案的缺陷
- **传统行锁 `SELECT ... FOR UPDATE`**：直接在数据库锁一整趟车或锁单个座位。高并发下导致写事务大量排队，瞬间耗尽线程池，并极易由于并发事务加锁顺序不一致产生 **Deadlock（死锁）**。
- **单纯扣减库存计数（Inventory Decr）**：无法支持区间座位精准重组，极易导致“长途有票、短途没票，但实际物理席位完全空闲”的局部库存碎片化。

## 2. 二进制区间图谱定义 (The Segment Bitmap Spec)

为了在内存中实现 **O(1) 时间复杂度** 的排他性区间判定，我们引入了 **二进制段位图（Segment Bitmap）** 概念：

### 2.1 掩码布局 (Bitmask Mapping)
一个座位的全部区间占用状态被压缩、折叠进一个 **Integer** 的二进制位中：

```text
  二进制低位 ◄────────────────────────────────────────────────────────── 二进制高位
  
  [位空间分配]   bit 0           bit 1           bit 2           bit 3 (保留)
  [物理段映射]  [物理区间段 1]   [物理区间段 2]   [物理区间段 3]   [未使用]
  [经停站表示]  (北京 ──► 天津)  (天津 ──► 济南)  (济南 ──► 上海)  
  [十进制权值]    2^0 = 1         2^1 = 2         2^2 = 4         2^3 = 8
```

### 2.2 购票请求转换公式 (Request to Segment Mask)
任何一笔购票请求传入 `from_seq`（始发站序号）和 `to_seq`（到达站序号），自动根据如下纯 ASCII 算式转化为**请求掩码（Request Mask）**：

```text
               to_seq - 1
  ReqMask =      ∑     ( 1 ◄◄ (i - 1) )
               i = from_seq
```

- **购票 [1 ──► 2] (北京-天津)**：覆盖区间 [1]，对应 `bit 0` 设为 1，`ReqMask = 1` (二进制 `001`)。
- **购票 [2 ──► 4] (天津-上海)**：覆盖区间 [2, 3]，对应 `bit 1, 2` 设为 1，`ReqMask = 2^1 + 2^2 = 6` (二进制 `110`)。
- **购票 [1 ──► 4] (北京-上海)**：全贯通，覆盖区间 [1, 2, 3]，对应 `bit 0, 1, 2` 全设为 1，`ReqMask = 1 + 2 + 4 = 7` (二进制 `111`)。

## 3. 第一防御线：Redis Lua 原子预占算法

为了拦截 99% 的超频请求，防止高并发写直接穿透到 MySQL，在 Redis 中每个物理座席均维护一个当前的**席位占用位图（Occupied Mask）**：
- **Key 格式**：`r:{schedule_id}:seat:{seat_id}` (存储当前已占用的十进制二进制整数值)。

### 3.1 无冲突锁座算式 (Bitwise Intersection Verification)
购票拦截不通过任何循环，直接执行超轻量级的原子位运算：

```text
  ┌────────────────────────────────────────────────────────┐
  │  [ 验证条件 ] : ( OccupiedMask  AND  ReqMask ) == 0    │
  └───────────────────────────┬────────────────────────────┘
                              │
               ┌──────────────┴──────────────┐
               ▼ (等于 0：表示无重叠，可售)    ▼ (不等于 0：表示区间冲突，拒绝)
       ┌──────────────────────────────┐     ┌──────────────────────────────┐
       │   位图重塑 (占位) :           │     │    返回 0 / ERROR             │
       │   OccupiedMask OR ReqMask    │     │   "席位在指定区间已售罄"      │
       └──────────────────────────────┘     └──────────────────────────────┘
```

### 3.2 极速预占 Lua 脚本逻辑 (Atomic Lua Script)
为了绝对避免“先查后改（Check-Then-Act）”的竞态条件，我们将校验与占位逻辑封装在一段原子 Lua 脚本中执行：

```lua
-- KEYS[1]: 席位 Key (r:{schedule_id}:seat:{seat_id})
-- ARGV[1]: 购票区间掩码 ReqMask (e.g. 3)

local occupied = redis.call('GET', KEYS[1])
local occupied_mask = 0
if occupied then
    occupied_mask = tonumber(occupied)
end

local req_mask = tonumber(ARGV[1])

-- 执行二进制位 AND 校验，大于 0 说明有区间重叠占用
if bit.band(occupied_mask, req_mask) > 0 then
    return 0 -- 锁座失败 (Collision)
else
    -- 无重合，执行位 OR 占用并写回
    local new_mask = bit.bor(occupied_mask, req_mask)
    redis.call('SET', KEYS[1], tostring(new_mask))
    return 1 -- 锁座成功 (Success)
end
```

## 4. 第二防御线：MySQL 物理事务升序行锁

当 Redis 第一防御线抢占成功后，请求进入写模型 MySQL。MySQL 内不保存任何“剩余票数计数器”，只保存原子的席位分段状态行：

### 4.1 数据表设计 (`seat_segment`)
```text
  ┌──────────────────────────────────────────────────────────────────────────────┐
  │                         Table: seat_segment                                  │
  ├──────────────┬─────────────────────┬──────────────┬──────────────┬───────────┤
  │    seat_id   │     segment_no      │  schedule_id │    state     │  version  │
  ├──────────────┼─────────────────────┼──────────────┼──────────────┼───────────┤
  │     201      │          1          │      99      │   HELD/CONF  │     1     │
  │     201      │          2          │      99      │   AVAILABLE  │     0     │
  │     201      │          3          │      99      │   AVAILABLE  │     0     │
  └──────────────┴─────────────────────┴──────────────┴──────────────┴───────────┘
```

### 4.2 升序强行锁，100% 杜绝死锁 (Deterministic Row-Locking Order ASC)
- **死锁诱因**：在高并发下，如果事务 A 先锁 `Segment 2` 再锁 `Segment 1`，而同时事务 B 先锁 `Segment 1` 再锁 `Segment 2`，两方在排他锁（`FOR UPDATE`）阶段将陷入永久循环互锁（Deadlock）。
- **硬核约束解法**：当旅客预订多站区间（如 1 ──► 3，包含 Segment 1, 2）时，SQL 加锁查询必须**强制进行升序（ASC）排序**：

```sql
SELECT id, state, version 
FROM seat_segment 
WHERE seat_id = 201 
  AND segment_no IN (1, 2) 
  AND schedule_id = 99
ORDER BY seat_id ASC, segment_no ASC 
FOR UPDATE;
```

**加锁顺序时序图表**：
```text
  时间轴 ──►
  
  [ 事务 A (预占 1-3段) ] ──► [锁 seat:201, seg:1] ──► [锁 seat:201, seg:2] ──► (抢占成功)
                                    │
                                    ▼ (排队等待锁释放)
  [ 事务 B (预占 1-2段) ] ───────► [等锁 seat:201, seg:1]
```
由于事务 B 同样被迫先对 `seg 1` 发起加锁，它会在 `seg 1` 的锁上排队，绝不会产生“事务 B 拿到了 seg 2 的锁去要 seg 1 的锁，而 A 拿到了 seg 1 的锁去要 seg 2 的锁”的环路死锁，从而从数据库物理层 100% 免疫死锁！

## 5. 写侧 CQRS 异步事件投影与最终一致性

本项目采用纯粹的 CQRS（读写分离架构），读侧的“高并发余票查询缓存（Availability Hash）”与写侧数据库状态并不共享事务。

### 5.1 发件箱模式自愈保序投递 (Transactional Outbox)
1. 数据库预占锁座事务中，伴随写入一笔 **OutboxEvent**（事件：`ORDER_PAID` / `RESERVATION_CANCELLED`）。
2. 发件箱发布器使用高效的批量撈取命令，毫秒级轮询 Outbox 表并发布到 Kafka：

```sql
SELECT * FROM outbox_event 
WHERE processed = 0 
ORDER BY id ASC 
LIMIT 100 
FOR UPDATE SKIP LOCKED;
```
`SKIP LOCKED` 避免了多 Worker 节点抢占事件的锁冲突，保证了超高的事件投递吞吐。

### 5.2 读模型回源重新推演 (Re-calculating Strategy)
当 Projector 消费到 `ORDER_PAID` 事件后，**不执行简单的 Redis 减 1 动作**（防漏发和重复消费），而是采取**自愈性最强的“重算推演”策略**：
1. 消费端根据事件中的 `schedule_id` 回源 MySQL，极速拉取该车次当前所有已锁定的 `seat_segment` 记录。
2. 异步将各区间的物理余票在内存中进行加和、打包，并通过 **Redis Pipeline** 一次性覆盖写入余票 Hash 缓存：
   - **Hash Key**：`q:availability:{schedule_id}:{seat_class}`
   - **Field 示例**：`1-2` -> `15` (表示区间 1-2 还剩 15 张物理座位)。

这套双防御、位掩码和最终一致性的完美闭环，使得中国中铁 12306 最核心、最棘手的车票核销算法在毫秒内便能彻底平稳降服，提供了无与伦比的技术弹性与生产安全性！

## 1. 业务基准假设 (Sizing Baseline & Hypotheses)

为了进行数学计算，我们设定以下符合中国铁路局真实开行方案的商业基准：

```text
  [ 每日开行列车 (Trains/Day) ] ──────► 1,000 趟列车
  [ 每趟列车平均站数 (Stations) ] ─────► 15 个经停站 (产生 14 个物理段/Segment)
  [ 每趟列车平均席位 (Seats) ] ────────► 1,000 个物理座位 (如商务舱/一等/二等总和)
  [ 每日售出车票 (Tickets/Day) ] ──────► 50,000,000 张 (五千万张票)
  [ 高并发峰值总流量 (Peak QPS) ] ──────► 50,000,000 次交互/秒 (99% 读, 1% 写)
```

## 2. 数据库存储容量估算 (Data Storage Sizing)

### A. 每日 MySQL 基础配席数据（静态与段锁数据）
每日开行 1000 趟车，每趟 1000 个座席，产生 1,000,000 个物理 Seat 记录。由于列车包含 15 个站，产生 14 个物理区间段（Segment Locks）。

#### ① 单条 SeatSegment 记录存储开销：
```text
  字段名称 (Field)       类型 (Type)          物理大小 (Bytes)
  id                     INT (Primary Key)    4
  schedule_id            INT (Foreign Key)    4
  seat_id                INT (Foreign Key)    4
  segment_no             TINYINT              1
  state                  VARCHAR(10)          10
  version                INT                  4
  -----------------------------------------------------------
  物理小计 (Row Size)                         ~27 字节 (考虑 InnoDB 页头与指针折合为 64 字节/行)
```

#### ② 每日段锁表记录数及存储体积：
```text
  [ 每日记录数 ] = 1,000 趟 * 1,000 席 * 14 段 = 14,000,000 行/天 (一千四百万行)
  [ 每日数据量 ] = 14,000,000 行 * 64 字节 = 896,000,000 字节 ≈ 896 MB/天
  [ 每日索引与元数据开销 (100% 冗余) ] ───────► 896 MB * 2 = 1.79 GB/天
  [ 年度物理存储总量 (Yearly Metadata) ] ─────► 1.79 GB * 365 ≈ 653 GB/年
```

---

### B. 每日购票事务数据（订单、票扣、发件箱）
每日成功售出 50,000,000 张车票（即 Command 事务）。产生 5000 万个 Ticket 记录、约 2500 万个 Order 订单记录（假设一次订单平均买 2 张票）以及 5000 万个 Outbox 发件箱事件记录。

#### ① 单条记录物理大小估算：
*   `Ticket` 行大小：约 **128 字节**（含车票号、车次、座位 ID、乘车人 ID、票价、状态）。
*   `Order` 行大小：约 **256 字节**（含订单号、支付流水号、总价、状态、创建时间）。
*   `Outbox_event` 行大小：约 **512 字节**（含事件全局唯一 ID、类型、聚合 ID、状态、JSON payload 契约体）。

#### ② 每日交易数据存储增量：
```text
  [ Ticket 每日大小 ] = 50,000,000 * 128 字节 = 6.4 GB/天
  [ Order 每日大小 ]  = 25,000,000 * 256 字节 = 6.4 GB/天
  [ Outbox 每日大小 ] = 50,000,000 * 512 字节 = 25.6 GB/天
  -------------------------------------------------------------
  [ 纯数据每日小计 ]                         = 38.4 GB/天
  [ 索引、冗余与事务日志 (MySQL Binlog/Undo, 150% 冗余) ] ─► 38.4 * 2.5 ≈ 96 GB/天
  [ 年度事务数据总量 (Yearly Transactions) ] ──► 96 GB * 365 ≈ 35,040 GB ≈ 35.04 TB/年
```

> **MySQL 存储选型建议**：
> 每日 96 GB 写入，一年沉淀 **35 TB** 强事务数据。
> 1. 采用 **MySQL 256个物理分片集群（Sharding）**，单物理分片承载 `35 TB / 256 ≈ 140 GB/年` 的轻量级存储，完美发挥 PCIe-4.0 NVMe SSD 的极致 IOPS 优势。
> 2. 对历史完结订单、已被 Projector 投影并消费成功的已处理发件箱事件（`processed=1`），由后台归档 Cron 线程每周定时迁移至冷数据层（如 Apache Iceberg / Hive 历史温区），主库只保全近 30 天的最热在线高并发活跃数据，主库磁盘水位长效锁定在 **5 TB** 以内。

## 3. 分布式缓存容量估算 (Redis Memory Sizing)

高并发读写分离（CQRS）下，全量最热列车的区间二进制占用位掩码（Bitmask）与快速可用余票统计，100% 缓存在 Redis Cluster 中。
*   保持最近 15 天开行的所有车次完全在 Redis 内存中。
*   活跃车次总数 = 1000 趟/天 * 15 天 = 15,000 趟列车。

### A. 席位区间位掩码哈希（r:{sched_id}:seat:{id}）
15,000 趟车 * 1000 个物理席位 = 15,000,000 个活跃席位 Key。
*   每个 Key 值为二进制整数（15个站，14个位，仅需 2 字节存储）。
*   在 Redis 内部，由于 `dictEntry`、`robj` 结构体及内存分配器（jemalloc）的对齐开销，一个 Key-Value 键值对折合消耗约 **150 字节**。

```text
  [ 席位位掩码内存总量 ] = 15,000,000 * 150 字节 = 2,250,000,000 字节 ≈ 2.25 GB (极轻量)
```

### B. 快速查询余票 Hash（q:availability:{sched_id}）
15,000 趟车 * 6 种座位席别 = 90,000 个余票缓存 Key。
每个 Key 内部为 Hash 结构，包含 105 个字段（15个站两两组合，即 `15 * 14 / 2 = 105` 个子区间）。每个字段值为整数。
*   在 Redis 内部，一个 105 字段的 Hash 约消耗 **12 KB** 内存。

```text
  [ 快速余票 Hash 内存总量 ] = 90,000 * 12 KB ≈ 1,080,000 KB ≈ 1.08 GB
```

> **Redis 内存选型建议**：
> 全系统最核心的抢票和余票读缓存在 Redis 内仅消耗 `2.25 + 1.08 ≈ 3.33 GB` 内存（即使加上各种系统 Overhead，单机不超过 **10 GB**）。
> 这说明：**12306 的 Redis 集群瓶颈根本不是内存容量（Capacity），而是单线程在万级高并发下的 CPU 执行 Lua 脚本的吞吐极限（IOPS）**。
> 因此，硬件选型时应优先选择 **高主频、低主频核数（如高频单核 4.0GHz+）** 的 CPU 机器充当 Redis Master 物理机，利用分片集群摊平 QPS。

## 4. 网络带宽估算 (Network Bandwidth Sizing)

### A. 读侧 QPS 带宽估算
在 49,500,000 QPS 读峰值下，假设平均每次 `GET /api/v1/query` 响应的极简 JSON 报文包大小为 **200 字节**：

```text
  [ 读侧裸网络吐吞量 ] = 49,500,000 次/秒 * 200 字节 = 9,900,000,000 字节/秒 = 9.9 GB/s
  [ 折合网络物理带宽 ] = 9.9 GB/s * 8 = 79.2 Gbps (万兆网络将瞬间爆裂塞满！)
```

> **读带宽 SRE 减压策略**：
> 这就是为什么 12306 必须且强制引入 **边缘网关本地内存缓存（L1 Local Cache）与 CDN 降维拦截**：
> 1. CDN 边缘及 BGP  Anycast 节点拦截 **90%** 的重复刷新请求（由于前一秒的票价和余票无任何实质变动，返回静态快照 100% 合理）。
> 2. 穿透至中央机房核心的 QPS 骤降至 `4,950,000 QPS`，核心网络带宽降为 **7.92 Gbps**，通过多活机房 4 条 10G 光纤专线对等均摊，完美保全机房内部核心。

### B. 写侧 TPS 带宽估算
在 500,000 TPS 并发预占/打单峰值下，每次 POST 购票请求报文大小约 **500 字节**，下单成功后生成的账单响应约 **500 字节**（共计 1,000 字节/事务）：

```text
  [ 写侧网络吞吐量 ] = 500,000 TPS * 1,000 字节 = 500,000,000 字节/秒 = 500 MB/s
  [ 折合网络物理带宽 ] = 500 MB/s * 8 = 4 Gbps (需要核心机房具备千兆级局域专网)
```

## 5. 消息队列 (Kafka Partition Sizing & Disk Retention)

所有的交易事务（`50,000,000 次/天`）通过 Outbox 事件投递到 Kafka 主题 `ticket_events` 中。

### A. 消息写入吞吐与分区选型：
*   **平均事件发布速率**：`50,000,000 / 86400 ≈ 578 EPS` (Events Per Second)
*   **巅峰写秒级突涌速率**：**500,000 EPS**（即 50 万写峰值瞬发至 Kafka）
*   **Kafka 分区 (Partitions) 数量规划**：
    > 消息队列的并行消费上限受限于 Partition 数量。
    > 为了支持 Projector 高并发消费（单实例消费速率约 `20,000 EPS`），同时完美对齐我们设计的 KEDA 自动弹性缩容最大 32 副本，
    > **物理硬锁 Kafka 主题 `ticket_events` 拥有 32 个 Partitions**。
    >
    > **消息路由 Routing Key**：一律以 `schedule_id`（车次计划ID）为 Key，利用 Hash 路由，确保**同一趟列车的所有订单和退票事件被精准、绝对保序地分发至同一个 Partition 内部**，彻底规避了因多分区乱序导致的缓存数据覆盖脏态。

### B. Kafka 磁盘存储积压容量（7天数据保留期）：
*   单条 Outbox Event Payload 约 512 字节。
*   每日写入总量 = `50,000,000 * 512 字节 = 25.6 GB/天`。
*   7天存储保留期 = `25.6 GB * 7 = 179.2 GB` 的轻量高速硬盘空间，无需过多磁盘堆叠，全盘配备高性能 SAS/NVMe 即可。

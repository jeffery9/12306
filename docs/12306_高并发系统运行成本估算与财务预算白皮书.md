# 12306 高并发票务系统 — 运行成本估算与 TCO 财务预算白皮书 (1亿级并发多路线对比版)

> **最高学术与工程准则**：本白皮书针对 12306 系统在 **1亿级 (100M CQS)** 极限吞吐配置下的物理机房硬件、多中心网络互联、高吞吐 CDN 及顶级 SRE 运维中心，建立了严密、可落地的 TCO (Total Cost of Ownership, 总拥有成本) 财务折算模型。本版加入了 **“五大技术路线（Python + MySQL、Go + PG、C# + PG、Rust + PG、Rust 终极降本栈）”** 极其精细、严格对齐的第一性原理物理算力与财务成本对比。全篇采用纯 ASCII 排版。

## 1. 财务模型假设 (Financial Hypotheses)

为了进行精确的成本推导，我们采用以下财务基准假设：
*   **计算模式**：**混合云模式（Hybrid Cloud）**。强事务的数据库、高性能缓存及消息队列部署于自建私有机房物理服务器（安全第一、低延迟）。无状态的 Web 网关服务（K8s Web Pods）及 CDN 边缘下沉节点，部署于公有云弹性算力池。
*   **硬件折旧周期**：服务器、交换机等物理资产统一按 **3 年双倍余额递减法** 计提折旧，折旧后残值设定为 **5%**。
*   **物理机房托管**：一线城市 Tier 3+ 标准数据中心，高功耗机柜（8kW/Rack）托收，机柜租用电力等综合均摊按 **¥8,000/个机柜/月**。

## 2. 1亿级 CQS 下五大技术路线架构规格核算 (Physical Sizing)

支持 1亿次/秒 (100M CQS, 99% 读, 1% 写) 时，物理服务器的需求量发生倍增：

### A. 无状态 Web API 层 Pods 与宿主机换算：
```text
  技术路线                单 Pod 吞吐(QPS)   所需 Pods 副本数   所需高密度物理宿主机数量 (2U/128C)
  ────────────────────────────────────────────────────────────────────────────────────────
  1. Python (FastAPI)     1,500 QPS          10,000 个 Pod      312 台 (4c/8g 严重限制)
  2. Go (Fiber)           28,000 QPS         400 个 Pod         12 台  (协程多核释放)
  3. C# (.NET 9 AOT)      24,000 QPS         500 个 Pod         16 台  (AOT 编译精纯机器码)
  4. Rust (Axum)          45,000 QPS         200 个 Pod         6 台   (Zero-GC 极致效率)
  5. Rust (终极微内核)    45,000 QPS         200 个 Pod         6 台   (极致边缘拦截 + 缓存合并)
```

### B. 缓存层 (Redis/Dragonfly) 物理节点换算：
*   **Redis 方案**：单线程架构，为均摊高并发 QPS，分片扩容至 256 组（一主一备共 512 台 1U 物理机）。
*   **Dragonfly 方案**：单物理机即可爆发 3,000,000+ QPS，仅需 **4 组（主备共 8 台 1U 物理机）** 即可。

### C. 数据库层 (MySQL/PostgreSQL/LSM IMDG) 物理节点换算：
*   **MySQL 方案**：单机写入极值约 2k TPS。需拆分成 512 个分片（主备共 1024 台 2U 物理机）。
*   **PostgreSQL 方案**：单机写入能级达 3.5k TPS。拆分为 286 分片（主备共 572 台 2U 物理机）。
*   **LSM IMDG 方案 (终极降本)**：席位状态驻留分布式强一致内存（10台 Raft 共识物理服务器），交易追加RocksDB。仅需 **10 台超高配物理机**。

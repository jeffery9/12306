# 12306 高并发票务系统技术方案

**版本：V1.0**  
**架构范式：CQRS + Event-Driven Architecture**  
**核心技术：Redis + MySQL + MQ + Transactional Outbox + CDC**  

---

# 1. 文档目标

本文设计一个面向 12306 类铁路客票系统的高并发票务交易平台。

系统必须同时满足：

1. 海量余票查询；
2. 高并发抢票；
3. 绝对禁止超卖；
4. 支持区间票务；
5. 支持座位级资源分配；
6. 查询与交易完全解耦；
7. 突发流量削峰；
8. 订单操作幂等；
9. MQ 重复投递可安全处理；
10. 交易数据最终可审计、可恢复；
11. 读模型允许短暂最终一致；
12. 核心交易模型保持强一致；
13. 单节点故障不能造成票务数据丢失；
14. 支持 Redis、MQ、Query Model 故障后的恢复和重建。

---

# 2. 核心架构原则

系统遵循六条第一性原理。

## 2.1 查询与交易彻底分离

```text
Query
    ↓
“现在看起来还有没有票？”

Command
    ↓
“这次请求是否真正获得了票？”
```

两者不是同一个问题。

---

## 2.2 Query Model 不是库存权威

查询系统返回：

```text
二等座：23
```

只能解释为：

> 当前读模型认为有 23 个可售资源。

不能解释为：

> 当前用户一定可以买到一张。

最终销售权由 Command Model 决定。

---

## 2.3 Command Model 是唯一销售权威

所有真正改变票务状态的操作必须进入 Command Domain：

```text
Create Order
Reserve Seat
Confirm Order
Cancel Order
Release Reservation
Refund
```

任何 Query Service 都不得修改票务状态。

---

## 2.4 Redis 是高速竞争控制层，不是最终账本

Redis 用于：

- 快速可用性判断；
- Reservation；
- 并发控制；
- TTL；
- 流量保护。

MySQL 用于：

- 持久化订单；
- 持久化票务状态；
- 审计；
- 恢复；
- 最终业务事实。

---

## 2.5 MQ 负责削峰和事件传播

MQ 不承担业务一致性本身。

必须配合：

```text
Idempotency
+
Transactional Outbox
+
Retry
+
DLQ
+
Compensation
```

---

## 2.6 票务不是简单库存，而是区间资源分配

普通商品：

```text
stock = 100
```

铁路客票：

```text
Train
  ↓
Carriage
  ↓
Seat
  ↓
Segment
```

例如：

```text
北京 → 天津 → 济南 → 南京 → 上海

S1    S2    S3    S4
```

某个座位：

```text
Seat 08A

S1 FREE
S2 SOLD
S3 SOLD
S4 FREE
```

因此：

```text
北京 → 上海
```

需要寻找一个：

```text
S1 + S2 + S3 + S4
```

全部可用的座位。

这决定了库存模型不能简单使用一个 count 字段。

# 6. 铁路区间模型

假设：

```text
A → B → C → D → E
```

定义：

```text
Segment 1 = A → B
Segment 2 = B → C
Segment 3 = C → D
Segment 4 = D → E
```

对于：

```text
A → D
```

需要占用：

```text
S1
S2
S3
```

对于：

```text
B → E
```

需要：

```text
S2
S3
S4
```

因此一个座位的占用状态可以表示为 Bitmap。

例如：

```text
Seat 08A

0000 = 全部空闲
0100 = S2 被占用
0110 = S2/S3 被占用
```

对于请求区间：

```text
A → D
```

生成 Mask：

```text
0111
```

判断：

```text
seat_bitmap & request_mask == 0
```

即可快速判断该座位是否可分配。



```text

```

```json

}
```

对于高性能实现，推荐 Bitmap / BitSet。

# 8. Reservation 状态机

核心状态：

```text
AVAILABLE
    │
    │ reserve
    ▼
HELD
    │
    ├──────────────┐
    │              │
 confirm        timeout
    │              │
    ▼              ▼
  SOLD          RELEASED
                   │
                   ▼
               AVAILABLE
```

状态转换必须是有限状态机，而不是任意 UPDATE。

允许：

```text
AVAILABLE → HELD
HELD → SOLD
HELD → RELEASED
```

禁止：

```text
SOLD → HELD
SOLD → AVAILABLE
RELEASED → SOLD
```

# 10. Redis Lua 原子预留

Redis 操作必须通过 Lua 或等价原子机制。

伪代码：

```lua
-- 1. 检查座位是否可用
-- 2. 检查请求区间是否冲突
-- 3. 设置 reservation
-- 4. 写入 TTL
-- 5. 返回 reservation_id
```

逻辑必须满足：

```text
Check
+
Reserve
+
TTL
```

原子完成。

不能：

```text
GET
↓
Python 判断
↓
SET
```

否则会产生 TOCTOU：

```text
T1 GET → FREE
T2 GET → FREE

T1 SET → HELD
T2 SET → HELD
```

造成超卖。


# 14. MQ 消费幂等

消费者不能假设 MQ Exactly Once。

必须按照：

```text
At Least Once
```

设计。

消费：

```text
receive message
     │
     ▼
check event_id
     │
     ├── processed → return
     │
     └── new
           │
           ▼
       DB transaction
           │
           ├── business mutation
           │
           └── insert event_id
           │
           ▼
          COMMIT
```

因此：

```text
event_id
```

必须具有唯一约束。

---

# 15. Transactional Outbox

禁止：

```text
BEGIN
UPDATE order
COMMIT

send MQ
```

因为：

```text
DB success
MQ failure
```

会导致状态丢失。

采用：

```text
BEGIN

INSERT order

INSERT outbox_event

COMMIT
```

然后：

```text
Outbox Publisher
       │
       ▼
      MQ
```

数据库事务保证：

```text
Business State
+
Event
```

同时成功。

# 18. 数据库最终防线

Redis 不是最终安全边界。

数据库必须再次验证。

例如：

```sql
UPDATE seat_segment
SET reservation_id = :reservation_id
WHERE seat_id = :seat_id
  AND segment_id >= :start_segment
  AND segment_id < :end_segment
  AND reservation_id IS NULL;
```

然后检查：

```text
affected_rows == required_segment_count
```

如果：

```text
affected_rows < required_segment_count
```

整个事务：

```text
ROLLBACK
```

这才是真正的防超卖底线。

# 19. Redis 与 MySQL 的一致性关系

需要明确：

```text
Redis Reservation
        ↓
暂时锁定
        ↓
MySQL Durable Commit
        ↓
最终确认
```

Redis 不是独立的永久账本。

因此必须处理：

### 情况 A

```text
Redis HELD
MySQL SUCCESS
```

正常。

---

### 情况 B

```text
Redis HELD
MySQL FAILURE
```

必须：

```text
RELEASE
```

---

### 情况 C

```text
Redis FAILURE
MySQL 未执行
```

直接失败。

---

### 情况 D

```text
Redis SUCCESS
MQ LOST
```

依靠：

```text
Outbox / Recovery
```

进行恢复。

# 25. Query 一致性策略

Query Model：

```text
Eventually Consistent
```

Command Model：

```text
Strongly Consistent
```

因此可能短时间出现：

```text
Query:
还有 1 张

Command:
已经没有
```

这是允许的。

但不允许：

```text
Command:
已经卖出

Query:
长期显示 1 张
```

因此必须设计：

```text
Projection Lag Monitoring
```

例如：

```text
projection_lag < 3s
```

超过阈值：

```text
Alert
```

# 26. Binlog CDC

MySQL Binlog 可以作为：

```text
CDC
```

同步：

```text
MySQL
 ↓
Binlog
 ↓
CDC
 ↓
Query Projection
```

作用：

1. 构建 Query Model；
2. 修复 MQ 丢失；
3. Projection 重建；
4. 数据审计；
5. 灾备恢复。

但：

> Binlog 不应该取代 Transactional Outbox 的业务事件语义。

# 27. 为什么 Outbox 与 CDC 可以同时存在

两者职责不同。

```text
Outbox
    ↓
业务事件

CDC
    ↓
数据库变化事实
```

Outbox：

```text
OrderConfirmed
```

CDC：

```text
orders.status changed:
PAYING → CONFIRMED
```

前者是：

> Domain Event

后者是：

> Data Change Event

两者不应该混淆。

```text

```




```text

```

之间具有明确的状态竞争规则。

# 35. 关键竞态：支付与超时

例如：

```text
T1 订单超时任务
T2 支付回调
```

同时发生。

不能：

```text
T1:
UPDATE status = EXPIRED

T2:
UPDATE status = CONFIRMED
```

最后谁覆盖谁。

应该使用状态条件：

```sql
UPDATE orders
SET status = 'EXPIRED'
WHERE id = ?
AND status = 'WAITING_PAYMENT';
```

支付：

```sql
UPDATE orders
SET status = 'CONFIRMED'
WHERE id = ?
AND status = 'WAITING_PAYMENT';
```

只有一个事务成功。

另一个：

```text
affected_rows = 0
```

然后根据实际状态处理。

# 36. 一致性等级

整个系统不追求“一切强一致”。

而是进行分层。

| 数据 | 一致性 |
|---|---|
| Query Availability | 最终一致 |
| Reservation | 强一致 |
| Order | 强一致 |
| Payment | 强一致 |
| Ticket | 强一致 |
| Analytics | 最终一致 |
| Notification | 最终一致 |
| Search Index | 最终一致 |

这是 CQRS 最重要的价值之一：

> **一致性不是系统级开关，而应该是 Domain 级策略。**

# 37. 故障处理

## Redis 故障

Query：

```text
L1 Cache
```

继续提供部分热点查询。

Command：

```text
拒绝新的 Reservation
```

不能：

```text

 ↓
直接打 MySQL
```

否则数据库会瞬间成为库存竞争中心。

# 38. MQ 故障

Command 不应该假设 MQ 永远可用。

因为已经写入：

```text
Outbox
```

所以：

```text
MQ DOWN
```

仍然可以：

```text
DB commit
```

等待 MQ 恢复后继续发布。

# 39. MySQL 故障

如果 Command Store 无法保证强一致：

```text

```

系统可以：

```text
Query 继续
Command 暂停
```

即：

```text
Read Available
Write Unavailable
```

这比：

```text
数据库异常仍继续卖票
```

安全得多。

# 43. 数据分片

MySQL 可以按照：

```text

```

进行水平分片。

例如：

```text

  2026-09-01 ~ 2026-09-07

DB02
  2026-09-08 ~ 2026-09-14
```

或者：

```text

```

但订单和库存需要考虑：

原则：

> **尽量让一个 Reservation Transaction 落在同一个数据库分片。**

避免分布式事务。

# 59. 最终架构结论

本方案不是简单地：

```text
Redis + MySQL + MQ
```

而是：

```text
             CQRS
               │
      ┌────────┴────────┐
      │                 │
   QUERY             COMMAND
      │                 │
 Read Model        Reservation
      │                 │
    Redis           Redis
                        │
                     State
                     Machine
                        │
                       MQ
                        │
                      MySQL
                        │
                     Outbox
                        │
                       MQ
                        │
                 Query Projection
```

其第一性原理是：

> **查询“有没有票”和决定“谁获得这张票”是两个完全不同的问题。**

Query Model 追求：

```text
Throughput
Latency
Availability
```

Command Model 追求：

```text
Correctness
Consistency
Concurrency Control
Durability
```

因此：

```text
Query ≠ Inventory Authority
```

而：

```text
Reservation ≠ Order
```

以及：

```text
Redis ≠ Durable Truth
```

最终形成四个清晰的责任边界：

```text
┌─────────────────────────────────────────────┐
│                  QUERY                      │
│  海量查询 / 读模型 / 最终一致 / 高吞吐       │
└──────────────────────┬──────────────────────┘
                       │
                       │ Advisory
                       ▼
┌─────────────────────────────────────────────┐
│               RESERVATION                   │
│  区间资源竞争 / 原子锁定 / TTL / 幂等        │
└──────────────────────┬──────────────────────┘
                       │
                       │ Durable Commit
                       ▼
┌─────────────────────────────────────────────┐
│                COMMAND                      │
│  Order / Ticket / Payment / Inventory       │
│  强一致 / 持久化 / 业务权威                  │
└──────────────────────┬──────────────────────┘
                       │
                       │ Domain Events
                       ▼
┌─────────────────────────────────────────────┐
│              PROJECTION                     │
│  Query Model / Cache / Analytics             │
└─────────────────────────────────────────────┘
```

**这就是 12306 类票务系统采用 CQRS 的真正意义：不是把读请求和写请求放到两个服务里，而是把“可售性观察”和“不可逆资源分配”建模成两个不同的计算问题，并让它们拥有不同的数据模型、一致性策略和性能优化路径。**

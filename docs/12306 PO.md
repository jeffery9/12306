基于前面那套**可运行的 12306 CQRS 技术设计**，如果目标不是做 Demo，而是做一个能够承受真实高并发、具备故障恢复和一致性验证能力的生产级系统，我会按下面规模估算。

# 3. 真正困难的不是 CRUD

这个项目最大的误区是：

> “Train、Seat、Order 几张表 + Redis + Kafka，应该很快。”

实际上 CRUD 只占整个工作量的一小部分。

真正消耗时间的是 **一致性和故障模型**。

### 工作量大致可以拆成：

```text
                    工作量
                     │
                     │
一致性 / 并发控制    ████████████████████  25%
故障恢复             ███████████████      18%
性能 / 压测          █████████████        15%
CQRS / Projection    ████████████         13%
Order / Reservation  ███████████          12%
Infrastructure       █████████            10%
普通 CRUD             █████               5%
测试                  ███                 2%
```

尤其是下面几个问题。

---

# 4. 最主要的技术工作量

## A. 座位区间库存模型

这是第一大难点。

不能简单：

```text
stock = stock - 1
```

而是：

```text
Seat
  │
  ├── Segment 0
  ├── Segment 1
  ├── Segment 2
  ├── Segment 3
  └── ...
```

例如：

```text
北京
 │
S0
 │
天津
 │
S1
 │
济南
 │
S2
 │
南京
 │
S3
 │
上海
```

北京 → 济南：

```text
mask = 0011
```

南京 → 上海：

```text
mask = 1000
```

两者可以同时占用同一座位。

因此需要同时解决：

* segment bitmap
* seat allocation
* overlapping reservation
* non-overlapping reservation
* Redis atomicity
* MySQL authoritative state
* reconciliation

这一块本身就可能需要 **3～4 周**。

---

# 5. Redis Lua 不是重点，状态语义才是重点

真正需要设计的是：

```text
AVAILABLE
    │
    ▼
  HELD
    │
    ├──────► RELEASED
    │
    ▼
CONFIRMED
    │
    ▼
TICKET_ISSUED
```

同时必须处理：

```text
Request Retry
     │
     ▼
Idempotency
     │
     ▼
Redis reservation
     │
     ▼
Kafka
     │
     ▼
DB transaction
     │
     ▼
Outbox
```

任何一个节点失败，都不能产生：

```text
钱扣了
但没有票

票占了
但订单不存在

订单存在
但库存没有扣

库存扣了
但 Query 永远显示有票
```

所以 **Reservation + Order + Inventory consistency** 是核心工作量。

---

# 6. Kafka / Outbox 需要约 3～4 人月

不是“加一个 Kafka dependency”这么简单。

需要实现：

```text
MySQL Transaction
      │
      ├── Order
      ├── Reservation
      └── Outbox Event
                │
                ▼
          Outbox Publisher
                │
                ▼
              Kafka
                │
       ┌────────┴────────┐
       ▼                 ▼
 Query Projector    Other Consumer
```

需要验证：

### DB 成功，Kafka 失败

```text
DB COMMIT
Kafka DOWN
       ↓
Outbox pending
       ↓
Kafka recovery
       ↓
republish
```

### Kafka 重复投递

```text
Event #123
   ↓
Consumer
   ↓
DB side effect
```

再次收到：

```text
Event #123
   ↓
processed_event
   ↓
already processed
   ↓
NO SIDE EFFECT
```

### Kafka 顺序

至少需要针对：

```text
schedule_id
```

保证同一列车的相关事件具有稳定顺序。

---

# 7. Query Side 实际上是另外一个系统

Query 不是：

```sql
SELECT count(*)
FROM seat;
```

而应该是独立的：

```text
Command DB
     │
     │ Event
     ▼
Projection
     │
     ▼
Redis Query Model
     │
     ▼
Caffeine
     │
     ▼
HTTP
```

最终查询：

```text
北京 → 上海
二等座
```

应该尽可能变成：

```text
Redis GET
```

而不是：

```text
Redis
  ↓ miss
MySQL
```

所以需要开发：

* Query Model
* Projection
* Projection idempotency
* version ordering
* cache invalidation
* cache rebuild
* projection reconciliation
* degraded mode

大约 **3～4 人月**。

---

# 8. 压测本身也不是一天能完成

至少应该做四层。

### Level 1：功能并发

```text
1 seat
10,000 requests
```

预期：

```text
success = 1
oversell = 0
```

---

### Level 2：区间竞争

```text
北京 → 天津
北京 → 济南
```

必须互斥。

而：

```text
北京 → 天津
南京 → 上海
```

允许同时成功。

---

### Level 3：系统级压力

例如：

```text
10K QPS
50K QPS
100K QPS
```

测试：

* Query QPS
* Redis latency
* Kafka lag
* MySQL TPS
* CPU
* GC
* connection pool
* network
* projection lag

---

### Level 4：Chaos

例如：

```text
Redis restart
Kafka restart
MySQL failover
Projector crash
Network partition
Consumer duplicate
Consumer delay
Outbox backlog
```

然后验证：

> 系统最终是否回到正确状态？

这一块建议至少 **3～4 周**。

# 9. 不同团队规模对应周期

这是比较重要的一个判断。

| 团队      |         MVP | Production V1 |
| ------- | ----------: | ------------: |
| 2 人     |       4～5 月 |        9～12 月 |
| 4 人     |     2～2.5 月 |         6～8 月 |
| 6 人     |     1.5～2 月 |         5～6 月 |

| 12 人    |     1～1.5 月 |         4～5 月 |
| 20 人    |       1 月左右 |         3～4 月 |

但是：

> **增加人手不会线性缩短周期。**

因为这里有大量强耦合工作：

```text
Inventory Model
       ↓
Reservation
       ↓
Order
       ↓
Outbox
       ↓
Kafka
       ↓
Projection
       ↓
Reconciliation
```

这些工作不能无限并行。

# 10. 我更推荐 6～8 人，而不是 15～20 人

如果这是一个从零开始的新系统，我会采用：

```text
              Tech Lead / Architect
                       │
        ┌──────────────┼──────────────┐
        │              │              │
   Command Team    Query Team    Infrastructure
      2～3人          2人             1～2人
        │              │              │
        └──────────────┼──────────────┘
                       │
                  QA / Performance
                       1人
```

也就是：

**6～8 人核心团队。**

原因是这个系统的关键不是“写很多代码”，而是：

> **让少数核心人员真正理解 Inventory → Reservation → Order → Event → Projection 的一致性链路。**

如果拆成 20 个人，很容易出现：

```text
A：Redis 我负责

B：Order 我负责

C：Kafka 我负责

D：Query 我负责
```

最后没人真正负责：

```text
全局一致性
```

  ↓

  ↓

  ↓

## 我的建议

如果你是在做**架构验证/技术面试/架构作品/企业级技术原型**，不要一上来做 6 个月版本。

直接做：

> **4 人 × 10 周 = 10 人月的完整 Vertical Slice**

但要求这 10 人月必须把最核心的东西做“真”：

```text
Segment Inventory
        ↓
Redis Lua
        ↓
Reservation
        ↓
MySQL Transaction
        ↓
Outbox
        ↓
Kafka
        ↓
Query Projection
        ↓
Redis Query
```

然后用：

```text
10,000 concurrent requests
+
故障注入
+
自动化一致性验证
```

证明它真的 **不超卖、可幂等、可恢复、最终收敛**。

这比做一个“功能很多、但库存只是 `stock--`”的半年项目，技术价值高得多。

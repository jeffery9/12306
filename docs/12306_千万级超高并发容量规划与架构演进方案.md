## 2. 5千万级 (50M) 峰值流量目标拆解 (The 50M CQS Deconstruction)

**5千万次/秒 (50,000,000 QPS/TPS)** 是超越双十一峰值数倍的极致海量并发。在真实的 12306 场景中，绝大多数流量来自于用户的疯狂刷新（读）。
根据二八定律与实际购票漏斗，我们按照 **99% 读流量与 1% 写流量** 进行物理拆解：

*   **总峰值吞吐**：50,000,000 CQS (Command Query per Second)
*   **读峰值 (Query)**：`49,500,000 QPS` (4950 万次查询/秒)
*   **写峰值 (Command)**：`500,000 TPS` (50 万次下单预占/秒)

要支撑这一量级，单中心架构必定崩溃，必须引入 **异地多活 (Active-Active Multi-Region)** 与 **边缘计算极光防御** 体系。

## 3. 读侧架构演进：4950 万 QPS 的三级缓存防御圈 (Query Defense)

不能让 4950 万 QPS 穿透到机房核心 Redis，必须将计算与缓存推向边缘与进程本地。

```text
  [ 49,500,000 QPS 狂暴读流量 ]
             │
             ▼ 1. 边缘节点防御 (CDN / Anycast 智能网关) ──────► 拦截 60% (约 30M QPS)
             │    - 返回前一秒的短时效静态余票快照。
             │
             ▼ 2. 本地内存网关 (L1 Cache: Nginx Dict / 进程内存) ─► 拦截 30% (约 15M QPS)
             │    - 部署 5000+ 无状态网关节点，接收 Kafka Projector 的 Pub/Sub 余票广播，
             │      直接在进程内存中返回 0 毫秒延迟数据。
             │
             ▼ 3. 分布式缓存中心 (L2 Cache: Redis Cluster) ─────► 最终承接 10% (约 4.5M QPS)
                  - 承接最实时的点对点长连查询，物理拆分成 100 个分片 (Shards)。
                  - 单 Shard 承担 45,000 QPS，处于 Redis 极度舒适的安全水位。
```

## 4. 写侧架构演进：50 万 TPS 的异步排队与数据分片 (Command Sharding)

50 万 TPS 的物理落盘不可能由单一或少量的 MySQL 集群承担。必须采用 **排队削峰 + Lua分片扣减 + MySQL 细胞化分片**：

### A. 极速排队机与写流控 (Virtual Waiting Room)
在进入 Redis 扣减前，引入类似 Nginx 层或前置网关的 **排队机（Token Bucket）**。将超出 50 万 TPS 的海量无效恶意点击拦截在门外，对合法请求下发 Token 排队号，削峰填谷。

### B. Redis 分片预占拦截 (Lua Bitmask Sharding)
*   将当前的 Redis 单点升级为 **Redis Cluster 分片集群 (如 256 个 Shard)**。
*   **路由规则**：按 `(Train_ID, Date)` 作为哈希槽 (Slot) 的 Routing Key。由于不同车次的数据绝不相交，可完美打散到 256 个节点上。
*   **并发算力**：单台 Redis 处理 2,000 TPS 的 Lua 位掩码，256 台完美吞下 500,000 TPS 峰值扣减。

### C. MySQL 细胞化分表落盘 (Cellular Database Sharding)
50 万次物理落盘/秒，按单机极值 2,000 TPS 算，需将数据库进行极致水平切分。
*   **分库分表维度**：采用 `Hash(schedule_id) % 256` 拆分出 **256 个物理 Database 集群 (一主多从)**。
*   每个主库仅需承担 `500,000 / 256 ≈ 1,953 TPS`，这一压力对于启用了 NVMe 固态的高性能 MySQL 节点毫无压力，行锁升序（ASC）机制依然 100% 生效，死锁率为 0！

## 5. 发件箱通道演进：千万级吞吐的消息管道 (Outbox Streaming)

原有的 `FOR UPDATE SKIP LOCKED` 虽然在几万 TPS 内游刃有余，但在单库面临数千 TPS，总和 50万 TPS 时，拉取器（Publisher）本身可能成为瓶颈。

```text
  [ 细胞化 MySQL 实例 001~256 ] ──► (本地事务写入 Outbox 表)
             │
             ▼
  [ 增量日志解析器 (Canary / Maxwell / Debezium) ]
             │ (取代 SKIP LOCKED 轮询，采用 Binlog 增量抓取，将数据库读取压力降为 0)
             ▼
  [ Kafka / Apache Pulsar 高吞吐集群 ] 
             │ (512+ Partitions 物理分区，按 Schedule_ID 严格保序)
             ▼
  [ 异步投影器 Projector Cluster ] ──► (批量合并事件，覆写 Redis 和 本地内存网关)
```
> **架构革新**：引入 **CDC (Change Data Capture)** 监听 MySQL Binlog 替代 `SKIP LOCKED` 轮询。事件变更被极致地无缝推送到 Kafka，真正达成单向零阻力的 CQRS 信息流。

## 6. 物理硬件容量估算与基建清单 (Infrastructure BOM)

要支撑这座 50M CQS 的数字长城，异地多活（两地三中心）基建估算如下：

| 基础设施类别 | 预估物理实例规模 | 核心职责与部署特征 |
| :--- | :--- | :--- |
| **接入层网关 (Edge/CDN)** | **5,000+** 节点 | 抵挡千万级恶意刷票、提供 L1 内存快照防穿透。 |
| **计算层容器 (K8s Pods)** | **10,000+** 实例 | FastAPI/Go 无状态服务池，执行 Pydantic 校验和路由。 |
| **缓存层 (Redis Cluster)** | **256~512** 分片 | 提供 Lua 位掩码原子防重与最终 L2 读视图。 |
| **数据库层 (MySQL 主库)** | **256** 物理集群 | 按车次+日期 Hash 分片，承载 50万 TPS 最终落地。 |
| **消息流枢纽 (Kafka/Pulsar)** | **100+** 高配 Broker | 保障读写最终一致性事件的分发、积压与缓冲。 |
| **网络层 (Networking)** | **Tbps 级** 带宽 | 两地三中心专线互联，BGP Anycast 多地就近分发。 |

> **总结**：
> 从 12306 当前的 MVP（CQRS + Redis Lua 预占 + ASC 升序锁）出发，底层并发理论（防死锁、读写分离）已经完全具备支撑千万级吞吐的数学完美性。通往 5 千万 QPS 的鸿沟仅仅是工程上的**水平细胞化切分（Sharding）**、**CDN 边缘下沉**以及**基建机器算力的堆叠**。系统的代码微观骨架将保持一致。

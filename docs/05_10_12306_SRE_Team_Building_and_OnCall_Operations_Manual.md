# 🛡️ 12306 生产级 SRE 组织架构、On-Call 响应与混沌工程演练白皮书

在 12306 这种涉及亿万国民出行、年度承载数十亿笔支付的“国之重器”级别系统中，任何单点故障都可能在社交媒体上引发海啸般的舆情。
再完美的双活容灾架构与防死锁并发代码，如果没有一支**纪律严明、高度自动化、具备极强应急肌肉记忆的 SRE（Site Reliability Engineering）运维团队**进行驾驭，系统依然会在春运洪峰中脆性崩盘。

本白皮书定义了 12306 SRE 团队的“三级火箭组织架构”、“故障应急响应矩阵”以及日常常态化的“混沌工程军演”纪律。

---

## 1. SRE 团队三级火箭组织架构 (The 3-Tier SRE Organization)

12306 的 SRE 团队摒弃了传统的“研发写代码，运维背锅”的割裂模式，采用 Google SRE 倡导的 **“You build it, you run it”** 融合模型，建立严格的三级防御梯队：

### 1.1 L1: NOC 监控中心 (Network Operations Center - 7x24)
*   **人员构成**：倒班制的一线监控工程师。
*   **核心职能**：7x24 小时死盯大屏（Grafana / 可观测性视图）。负责处理所有已知的、有明确 SOP（标准作业程序）的手册型告警（如：某 K8s Pod OOM，按手册点击重启）。
*   **升级红线**：若故障发生后 **3 分钟内** 无法通过 SOP 解决，或遇到未知的核心服务飙红，必须立刻升级（Escalate）至 L2。

### 1.2 L2: SRE 平台与应急专家 (Site Reliability Engineers)
*   **人员构成**：懂架构、精通 Python/Go 与 K8s 底层的软件工程师。
*   **核心职能**：
    *   **50% 时间**：参与业务代码应急排障、执行异地双活流量切换、数据库临时扩容、执行紧急限流与降级指令。
    *   **50% 时间**：编写 SRE 自动化脚本（减少 Toil 琐事）、研发内部巡检工具、固化新的 SOP 手册赋能给 L1。
*   **升级红线**：若遇到深度的代码级死锁、Redis LUA 严重 Bug、底层数据分片脏写，超过 **10 分钟** 无法止血，立刻升级至 L3。

### 1.3 L3: 核心研发与首席架构师 (Core Devs & Principal Architects)
*   **人员构成**：系统底层核心模块的原作者（如负责段位图算法的 Dev，负责 MySQL MGR 的 DBA）。
*   **核心职能**：处于 On-Call 待命的最底层防线（兜底者）。平时进行特性开发，当 L2 宣告无法处理的毁灭性 P0 故障时，由 L3 强行介入进行代码级热修复或架构级熔断。

## 2. On-Call 轮值与黄金 5 分钟响应矩阵 (On-Call & Escalation Matrix)

为了防止运维团队疲劳驾驶，12306 实行严格的 **On-Call 轮转制（Follow the Sun / 轮班制）**，并依托如 PagerDuty、钉钉/企微的极速告警电话机器人，执行“黄金 5 分钟”生命线。

### 2.1 故障定级标准 (Severity Levels)
*   **P0（毁灭级）**：主交易链路（购票/支付）完全中断，或发生跨机房数据脑裂。**要求：1 分钟内电话叫醒，5 分钟内全员上线处理。**
*   **P1（严重级）**：购票成功率跌破 95%，或某个地区（如南方局）大面积排队严重超时。**要求：3 分钟内响应，15 分钟内止血。**
*   **P2（较高故障）**：非主链路中断（如退票、历史订单查询页面 502），或某台非核心 Redis 节点宕机但已自动主从切换。**要求：15 分钟内响应。**
*   **P3/P4（警告级）**：日志报个别 500 错误、磁盘使用率达到 80%。**要求：工作时间处理（NOC 按 SOP 处置）。**

### 2.2 故障响应“1-5-10”铁律
针对 P0/P1 故障，12306 SRE 团队强制执行以下时效红线：
1.  **1 分钟发现（MTTD < 1m）**：通过 Prometheus + AlertManager，系统异常必须在 1 分钟内触发智能电话外呼，打爆当前 On-Call 工程师的手机。
2.  **5 分钟定位与响应（MTTA < 5m）**：On-Call 工程师必须在 5 分钟内打开电脑，登录应急指挥群（War Room），确认故障影响面并宣告“我已接管（ACK）”。
3.  **10 分钟止血（MTTR < 10m）**：10 分钟内必须下达止血指令（如：切机房、触发大面积限流、熔断非核心微服务）。**切记：此时的重点是“止血恢复服务”，而不是“排查代码找 Bug”。**

## 3. 混沌工程与日常军演日 (Chaos Engineering & GameDays)

真正的 SRE 团队不是在故障发生时才学会救火，而是常态化地“主动放火”。12306 引入了混沌工程（Chaos Engineering）理念，每月定期在生产环境/仿真环境开展 **“红蓝对抗军演（GameDays）”**。

### 3.1 破坏性注入清单 (Chaos Injection Roster)
由蓝军（混沌引擎如 Chaos Mesh / Litmus）在日常随机时段自动注入以下真实物理故障，检验红军（SRE 与自动容灾大坝）的接管能力：
1.  **拔线军演（Network Partition）**：随机物理 `iptables drop` 阻断北京与上海之间的专线，强制验证武汉仲裁中心的拉票决策和 1.5s 物理容灾接管是否生锈。
2.  **机房断电（Power Outage Monkey）**：强行 `kill -9` 关闭某个计算节点的全部 K8s Kubelet，验证 KEDA 弹性伸缩和 Envoy 熔断的漂移速度。
3.  **缓存击穿雪崩（Cache Avalanche）**：瞬间清空某台 Redis 物理分片的全部段位图缓存。验证 `projector` 从 MySQL 向 Redis 回源暖身的限流机制，确保 MySQL 不被瞬间穿透压死。
4.  **CPU 与 I/O 满载（Resource Exhaustion）**：在 MGR 数据库节点注入 `dd` 磁盘高频读写或 `stress` 打满 CPU，验证系统的自适应排队大坝是否能根据 TPS 自动拉长排队等待时间。

### 3.2 军演红线法则
*   **爆炸半径控制（Blast Radius）**：所有混沌实验必须在有业务低谷期（如凌晨 2:00-4:00）或专门的“金丝雀灰度流量”上进行。若监控大盘显示购票成功率跌破 99%，**死人开关（Dead Man's Switch）** 必须瞬间终止所有破坏性实验。

## 4. 无指责故障复盘文化 (Blameless Post-mortem)

当真实故障发生并最终修复后，12306 SRE 团队拒绝“抓替罪羊”和“开除程序员”的低级管理模式。每一场 P0/P1 故障的终点，是一份高规格的 **无指责复盘报告（Blameless Post-mortem）**。

### 4.1 为什么必须“无指责”？
如果故障发生后追究“是谁写出的这个 Bug”、“是谁敲错了这行命令”，工程师在应急时就会互相推诿、掩盖真相，甚至为了不背锅而隐瞒关键日志。
**12306 SRE 的核心信仰**：如果是人敲错了命令导致机房瘫痪，那不是人的问题，而是**系统设计缺乏防呆机制（Poka-yoke）、自动化工具缺乏边界检查的系统性缺陷**。

### 4.2 复盘根因分析（5-Whys RCA 模型）
复盘报告强制采用丰田的 **“5-Whys（连续问 5 个为什么）”** 直击灵魂深处：
*   **现象**：上海机房发生了 3 分钟的购票全线崩溃。
    *   **Why 1（为什么崩溃？）**：因为 Redis 内存瞬间耗尽，触发 OOM 宕机。
    *   **Why 2（为什么内存耗尽？）**：因为有一批非热门车次的历史旧缓存未设置 TTL 过期时间，占满了内存。
    *   **Why 3（为什么没设置 TTL？）**：因为研发在上周发版时，`redis_client.py` 里的 `set` 漏传了 `ex` 参数。
    *   **Why 4（为什么漏传参数还能上线？）**：因为针对 Redis 工具类的 Unit Test 代码覆盖率不足，未覆盖无 TTL 场景。
    *   **Why 5（为什么测试覆盖率不足没有拦截发布？）**：因为 CI/CD 流水线的 `SonarQube` 强制阈值检查被某研发在紧急发版时人为禁用了。

### 4.3 故障 Action Items (AIs) 的强制闭环
找到根因后，必须产出且强制落地的 Action Items（修复计划）：
1.  **架构修正**：在 `redis_client.py` 底层封装中，强制要求所有写入必须携带 TTL，否则编译抛错。
2.  **SRE 管控**：收回所有研发强行绕过 CI/CD 质量阈值的物理权限，建立应急发布（Emergency Hotfix）的双人审批流。
3.  **监控补漏**：增加 Prometheus 监控告警项：“Redis 内存增速异常预警（超过 1GB/min 时）”。

通过这种极其残酷但“对事不对人”的复盘闭环，每一次故障都会化为 12306 系统永不再犯同一错误的系统级抗体。
